# Point Cloud Display Scheme V2（高性能，PointCloud2为基线）

## 1. 背景与目标 (Background & Goal)

当前项目（PlasmaRobot）已实现基于 PCL 和 VTK 的点云显示方案（Point V1）。V1 方案在处理低分辨率或静态点云时表现良好，但在处理高帧率（30FPS+）、高分辨率（如 Realsense D435i 的 1280x720）实时点云流时，面临 CPU 瓶颈和内存带宽限制，且在交互（旋转/缩放）时易因渲染同步与 Z 缓冲精度问题导致画面闪烁（花屏）或卡顿。

本方案（Point V2）以官方 ROS 包发布的 **PointCloud2** 流为默认基线，强调在既有链路（[ros_worker.h](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/ros_worker.h)、[point_deal.cpp](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/point_deal.cpp)、[main_gl.cpp](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp)）上的高效优化。同时保留“深度+RGB 的 GPU 路线”作为增强选项。

## 2. 现有环境 (Environment)

*   **OS**: Linux
*   **Qt**: 6.7.2
*   **VTK**: 9.3.0
*   **PCL**: 1.15.0
*   **ROS2**: Galatic
*   **Hardware**: Intel Realsense Depth Cameras

## 3. 参考架构分析 (Reference Architecture Analysis)

参考 `func_real/pointcloud_architecture` 中的 Realsense Viewer 实现，其核心优势在于：

1.  **全 GPU 流水线 (Full GPU Pipeline)**:
    *   避免在 CPU 上进行 `Depth -> PointXYZ` 的繁重计算。
    *   避免每帧将数百万个点的 XYZ 坐标从 CPU 内存上传到 GPU 显存（PCIe 带宽瓶颈）。
2.  **基于纹理的渲染 (Texture-based Rendering / VTF)**:
    *   **数据载体**: 点云数据不存储在 Vertex Buffer (VBO) 中，而是存储在 **浮点纹理 (Floating Point Textures)** 中。
    *   **几何体**: 渲染时使用一个固定的 Grid Mesh（仅包含 UV 坐标）。
    *   **顶点着色器**: 通过 UV 坐标采样“位置纹理”来获取顶点的实际 3D 空间位置。

## 4. Point V2 技术方案 (Proposed Solution)

结合本项目基于 Qt6 和 ROS2 的特点，Point V2 建议采用以下架构：

### 4.1 数据流设计 (Data Flow)

**默认路线：PointCloud2（可靠优先）**：
`Camera -> ROS2 (PointCloud2) -> PCL/VTK 转换 -> 颜色直传 -> VTK Actor -> GPU Render`
*优点：无需自研反投影数学与 Shader，直接复用官方算法输出，可靠性高、集成快。*
*注意：PointCloud2 带宽和序列化成本较高，需在本地转换管线做性能优化（见 4.4）。*

**增强路线：深度+彩色（性能优先）**：
当需要更高帧率、更低延迟时，可切换到“深度+RGB + GPU Shader”流水线：

`Camera -> ROS2 (Depth Image + Color Image) -> GPU Texture Upload -> Compute/Fragment Shader (Deprojection) -> XYZ Texture -> Vertex Shader Render`

### 4.2 核心模块设计

#### A. 数据接收层 (ROS2 Receiver)
以 PointCloud2 为默认基线，同时支持增强路线：
*   默认：订阅 `/camera/depth/color/points` (PointCloud2)。
    - 本项目已有 [ros_worker.h](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/ros_worker.h#L23-L41) 的订阅实现，直接可复用。
    - 通过 [point_deal.cpp](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/point_deal.cpp) 将 PointCloud2 转换为 VTK PolyData，并在 [main_gl.cpp](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp#L910-L979) 中更新 Actor。
*   备选：订阅 `/camera/depth/image_rect_raw` (深度图) 与 `/camera/color/image_raw` (RGB图)，用于后续高性能 GPU 路线。

**订阅策略与 QoS（业界最佳实践）**
- 使用 `rclcpp::SensorDataQoS()`（通常为 Best Effort），确保与相机数据流匹配并减少丢包与阻塞。（参考 ROS2 Cookbook）
- 在同进程内启用零拷贝：`rclcpp::NodeOptions().use_intra_process_comms(true)`，降低消息拷贝成本。
- 如需多订阅并行处理，使用 `rclcpp::executors::MultiThreadedExecutor`（本项目已采用）并将回调放入独立回调组。

#### B. 渲染层 (Custom OpenGL Renderer)
考虑到 VTK 9.3 的封装较厚，直接在 VTK 中实现自定义 Shader较为复杂，建议采用 **混合模式** 或 **纯 OpenGL 模式**：

**方案 A: 基于 QOpenGLWidget 的原生渲染 (推荐用于极致性能)**
创建一个继承自 `QOpenGLWidget` 的控件 `PointCloudGLWidget`：
1.  **Texture Upload**: 将接收到的深度图和 RGB 图直接上传为 OpenGL 纹理 (`GL_R16` 或 `GL_R32F`)。
2.  **Point Generation**:
    *   使用 Fragment Shader 或 Compute Shader，根据内参矩阵，将 Depth Texture 的每个像素反投影 (Deproject) 为 3D 坐标，写入到一个 **XYZ Texture** (GL_RGB32F)。
3.  **Rendering**:
    *   绑定 XYZ Texture 和 RGB Texture。
    *   绘制一个分辨率为 `W x H` 的 Point Grid。
    *   在 Vertex Shader 中采样 XYZ Texture 确定顶点位置。
    *   在 Fragment Shader 中采样 RGB Texture 进行着色。

**方案 B: 基于 VTK 的自定义 Mapper (兼容性好)**
如果必须保留 VTK 的交互功能（如现有的裁剪、测量工具）：
1.  继承 `vtkPolyDataMapper` 或使用 `vtkShaderProperty`。
2.  注入自定义的 Vertex Shader 代码，替换默认的几何处理逻辑。
3.  通过 `vtkTextureObject` 传递深度图。
*(注：VTK 9.3 对 Shader 的自定义支持较好，但实现难度高于方案 A)*

### 4.3 关键技术点

1.  **Vertex Texture Fetch (VTF)**: 确保 OpenGL 上下文版本 >= 3.0 (Qt6 默认支持)。
2.  **GLSL Shader 实现**:
    *   *Deprojection*: `z = depth * scale; x = (u - cx) * z / fx; y = (v - cy) * z / fy;`
3.  **多线程优化**: ROS 回调在独立线程接收数据，OpenGL 渲染在 GUI 线程（或独立的渲染线程），需使用原子变量或双缓冲机制同步纹理上传。

### 4.4 基于 PointCloud2 的高效处理（业界最佳实践）
为保证在 PointCloud2 路线下的实时性，建议在转换与渲染环节进行以下优化，并说明其优势与相对于 V1 的改进：
- 复用 Mapper/Filter（降低频繁构建开销）
  - 优势：避免每帧 `new`/`delete` 导致的 CPU 抖动与内存碎片，减少管线重建时间。
  - 做法：初始化一次 `vtkVertexGlyphFilter` 与 `vtkPolyDataMapper` 为类成员变量，后续每帧仅需调用 `SetInputData` 更新数据引用。
  - 相对 V1 的改进：
    - **V1 做法**：在 [main_gl.cpp:onRosCloudFinished](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp#L910-L979) 中，每当收到新的点云数据（`resultCloud`），都会执行 `vtkVertexGlyphFilter::New()` 和 `vtkPolyDataMapper::New()`。这意味着每一帧都在销毁旧的渲染管线并重建新的，导致不必要的 CPU 开销。
    - **V2 做法**：在初始化阶段创建 Mapper 和 Filter，运行时仅更新数据源。这能显著稳定帧间延迟（Frame Time）。
- 颜色直传（DirectScalars，跳过 LUT）
  - 优势：直接使用 PointCloud2 的 RGB 字段作为点颜色，避免构建/更新查找表（LUT）与标量范围计算开销。
  - 做法：将 RGB 映射为 `vtkUnsignedCharArray`，命名 `"Colors"`；启用 `mapper->SetScalarModeToUsePointFieldData()`、`SelectColorArray("Colors")`、`SetColorModeToDirectScalars()`。
  - 相对 V1 的改进：
    - **V1 现状**：V1 代码中包含两部分逻辑。一部分是 PCD 文件加载（[main_gl.cpp:LoadPCDPoint](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp#L418-L455)），它使用了 LUT（查找表）进行着色，这部分是**测试代码，无需优化**。另一部分是 ROS 实时流处理（[main_gl.cpp:onRosCloudFinished](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp#L910-L979)），虽然已使用了 `DirectScalars`，但由于上述的“每帧重建 Mapper”问题，其性能优势未被完全释放。
    - **V2 做法**：明确区分测试代码与生产代码。在 ROS 实时渲染路径中，坚持使用 `DirectScalars` 并配合 Mapper 复用，确保零 LUT 开销。
- 批量预分配与容器复用（降低内存分配与拷贝）
  - 优势：降低频繁的 `Resize/Allocate` 成本，减少堆分配次数与数据搬运。
  - 做法：
    - **预分配**：根据传感器分辨率（如 1280x720）预先分配 `vtkPoints` 和 `vtkUnsignedCharArray` 的内存容量（`Allocate(capacity)`），避免在插入点时发生多次自动扩容。
    - **容器复用**：不要在每帧回调中 `New` 新的 `vtkPoints` 对象。建议维护一对“双缓冲”容器或复用同一个长生命周期的容器对象，每帧调用 `Reset()` 清空数据但保留内存块，然后填入新数据。
  - 相对 V1 的改进：
    - **V1 做法**：在 [point_deal.cpp:RosToVtkTask::run](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/point_deal.cpp#L145-L230) 中，每次任务执行时都会 `vtkPoints::New()` 创建新对象。虽然调用了 `Allocate`，但这是一个全新的内存申请操作，随后该对象被传递给主线程并在渲染后销毁。这种“用完即弃”的模式在高频（30Hz+）下会给内存分配器带来压力。
    - **V2 做法**：引入对象池或双缓冲机制，复用已分配好内存的 VTK 容器，仅做数据覆写，极大减少内存碎片和分配耗时。
- 迭代器直写（跳过 PCL 中间转换）
  - 优势：减少一次 `PointCloud2 → pcl::PointCloud → VTK` 的中间数据结构转换与拷贝，在高分辨率帧下效果显著。
  - 做法：使用 `sensor_msgs::PointCloud2Iterator` 直接遍历 `x/y/z/rgb` 字段，将数据写入预分配的 VTK 容器。
  - V1 举例与对比：当前 V1 已实现“直写”思路，但采用裸指针解析字段偏移（见 [point_deal.cpp:RosToVtkTask](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/point_deal.cpp#L167-L206)），这种方式易受字段布局变动、对齐与大小端影响；V2 使用官方迭代器接口，在保持“零中间结构”的同时提升健壮性与可维护性。
  - 为什么能减少一次转换与拷贝：若采用 `pcl::fromROSMsg`，需要先把 PointCloud2 的字节流拷贝并重组为 `pcl::PointCloud<T>`（一次大拷贝/重排），再从 PCL 容器写入到 VTK 容器（第二次拷贝）。迭代器直写路径是“从 PointCloud2 直接写到 VTK”，只做一次线性遍历与写入，减少一次中间结构构造与内存拷贝。
- 线程解耦与队列（保持 UI 流畅）
  - 优势：转换与可能的过滤在后台线程执行，UI 线程仅做 Mapper 输入更新与渲染，避免界面卡顿。
  - 做法：延续 `RosWorker → PointDeal → MainOpengl` 的信号槽与线程模型，必要时使用环形缓冲或丢旧帧策略。
  - 相对 V1 的改进：V1 已有解耦基础，V2进一步强调“前台仅更新渲染后端”的原则，减少 UI 阻塞。
- 可视窗口裁剪/采样（控制显示点数）
  - 优势：在相机当前视域内显示必要部分或进行下采样，降低绘制负载，提升帧率。
  - 做法：根据相机位姿或 ROI 做视锥裁剪；在超大分辨率时按比例采样。
  - 相对 V1 的改进：V1 以完整点集渲染为主，V2引入动态裁剪/采样以适配实时场景。
- PCL 过滤链（可选，提升质量与控制规模）
  - 优势：通过体素下采样（VoxelGrid）、PassThrough/裁剪、统计离群滤波（StatisticalOutlierRemoval）等常用算子，在保证形状特征的同时控制点数与去噪。
  - 做法：当需要 PCL 算法链时，先 `pcl::fromROSMsg` 转换为 `pcl::PointCloud<T>` 执行过滤，再写回 VTK 容器。
  - 相对 V1 的改进：V1 若直接全量显示，噪点与点量可能偏高；V2鼓励根据场景选择过滤器组合，平衡质量与性能。

### 4.5 交互稳定性优化（解决花屏与闪烁）

针对 V1 方案在交互（旋转、缩放）时出现的“花屏”（Z-fighting、画面撕裂或闪烁）现象，经过分析主要由以下原因导致，V2 方案将针对性解决：

1.  **Z-buffer 精度不足（Clipping Range 异常）**
    *   **原因分析**：VTK 默认开启 `AutoAdjustCameraClippingRange`。深度相机（如 Realsense）常输出离群噪点（如深度为 0 或极大值），导致点云的 Bounding Box 变得极大。为了包裹这些噪点，VTK 会将相机的 Clipping Range（近裁剪面与远裁剪面之距）设置得非常大。这导致有限的 Z-buffer 精度（通常 24-bit）被拉伸分布在巨大的深度范围内，使得近处物体的深度分辨率极低，产生 Z-fighting（点的前后遮挡混乱、闪烁）。
    *   **V2 解决方案**：
        *   **离群点过滤**：在转换阶段（`rosCloudFinished` 前）过滤掉 `NaN`、`Inf` 以及坐标值为 0 或极大的噪点，确保 Actor 的 Bounds 紧凑。
        *   **手动管理 Clipping Range**：每帧更新后，基于有效点云的 Bounds 调用 `renderer->ResetCameraClippingRange(bounds)`，或设置一个合理的固定范围（如 0.1m ~ 100m），避免自动计算引入的精度坍塌。

2.  **渲染频率过高与同步问题**
    *   **原因分析**：V1 的交互样式（如 [main_gl.cpp:RectDrawStyle::OnMouseMove](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/main_gl.cpp#L78-L94)）中直接调用 `renderWindow()->Render()`。在高回报率鼠标（1000Hz）下，这会触发极高频的渲染指令，可能导致 GPU 队列阻塞或与 Qt 的窗口合成器（Compositor）冲突，产生画面撕裂。此外，若 Render 期间后台正好在更新 Mapper 数据，也会导致未定义行为。
    *   **V2 解决方案**：
        *   **使用 Qt 事件循环调度**：在交互回调中调用 `widget->update()` 而非直接 `Render()`。这会触发 Qt 的 `paintGL`，利用 Qt 的 VSync 机制和事件合并能力，将渲染帧率限制在显示器刷新率（通常 60Hz），平滑画面。
        *   **双缓冲数据更新**：结合 4.4 节提到的容器复用，确保渲染线程读取的是“前台缓冲区”，而数据线程写入的是“后台缓冲区”，写入完成后原子交换引用，杜绝读写冲突。

3.  **QVTKOpenGLNativeWidget 兼容性**
    *   **原因分析**：Qt6 与 VTK9 集成时，`QVTKOpenGLNativeWidget` 对 OpenGL 上下文和 Surface Format 有特定要求。
    *   **V2 解决方案**：确保在 `main.cpp` 或 Widget 初始化前调用 `QSurfaceFormat::setDefaultFormat(QVTKOpenGLNativeWidget::defaultFormat())`，保证深度缓冲区（Depth Buffer）正确分配（通常 24-bit 或 32-bit）。

**转换策略对比**
- 快速路径（推荐）：迭代器直写 VTK（降低拷贝与分配），适合只做显示与轻微后处理的场景。  
  - V1 做法示例：在 [point_deal.cpp](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/point_deal.cpp#L145-L230) 的 RosToVtkTask 中，直接读取 PointCloud2 的二进制缓冲区，按字段偏移解析 x/y/z 与 rgb（使用裸指针 + reinterpret_cast），并将坐标与颜色写入 VTK 容器，最后构建 vtkPolyData 返回。  
  - V2 建议：改用 `sensor_msgs::PointCloud2Iterator` 进行字段遍历，避免手写偏移与类型别名，降低维护风险与数据对齐问题；性能基本等同，代码更稳健、可读性更高。
- 兼容路径：PCL 算法链（功能丰富但更重），适合需要精确滤波/裁剪/分割的场景。

**整体收益与相对于 V1 的优势**
- 更低的 CPU 占用与更稳定的帧间延迟（容器与对象复用、直写路径）。
- 更高的实时帧率（DirectScalars 颜色直传、动态裁剪/采样）。
- 更好的交互响应（线程解耦、前台轻渲染）。
- 更灵活的质量/性能平衡（可选的 PCL 过滤链）。

## 5. 预期收益 (Expected Benefits)

1.  **CPU 占用率大幅降低**: 点云生成移至 GPU。
2.  **带宽节省**: 传输深度图 (2MB) 比传输点云 (10MB+) 节省大量带宽。
3.  **帧率提升**: 支持 60FPS+ 的流畅渲染。

## 6. 迁移计划（默认采用 PointCloud2，含优化清单）

- 阶段 0：准备与基线确认
  - 确认 ROS2 相机节点发布 `/camera/depth/color/points`（PointCloud2）。
  - NodeOptions 设置 `use_intra_process_comms(true)`，Executor 使用 `MultiThreadedExecutor`。
  - 在 [ros_worker.h](file:///home/larusxu/CodeSpace/PlasmaRobot/src/plasma_gui/src/gui/work_space/opengl/point_v1/ros_worker.h) 保持 `SensorDataQoS()` 订阅策略。
  - 保持 V1 架构：`RosWorker → PointDeal → MainOpengl` 的线程解耦与信号链路。

- 阶段 1：V2 基线接入（复用 PointCloud2 链路）
  - 在 V2 页面中复用 V1 的控件与类（或封装为 V2 容器），确保：
    - `RosWorker::cloudReceived(msg)` → `PointDeal::requestConvertRosToVtk(msg)`。
    - `PointDeal::rosCloudFinished(polyData)` → `MainOpengl::onRosCloudFinished(polyData)`。
  - 渲染端确保首次接收点云后相机重置为点云 Bounds，设置点大小（示例：3.0）。
  - 验证 build（`colcon build`）与运行时刷新（可用 rosbag 或实时相机）。

- 阶段 2：性能与稳定性优化（PointCloud2 路线）
  - **核心性能优化**（参考 4.4）：
    - **迭代器直写（核心）**：使用 `sensor_msgs::PointCloud2Iterator` 遍历数据，直接填充预分配的 VTK 容器，跳过 PCL 中间结构。
    - **容器与对象复用**：将 `vtkPoints`、`vtkPolyDataMapper`、`vtkVertexGlyphFilter` 等重对象提升为类成员，初始化一次，运行时仅调用 `Reset()` 和 `SetInputData`，避免每帧 `New/Delete`。
    - **颜色直传（DirectScalars）**：映射 RGB 字段为 `vtkUnsignedCharArray`，启用 `SetColorModeToDirectScalars()`，彻底移除 LUT 计算开销。
  
  - **可选增强**：
    - **线程模型**：维持转换与渲染线程分离，考虑引入双缓冲机制防止读写冲突。

- 阶段 3：交互能力复用与增强
  - 复用 V1 的裁剪、移动、标签等交互逻辑到 V2 页面（保持 `EnableCrop/EnableMove/EnableLabel` 等接口一致）。
  - 保持交互样式与渲染器绑定关系，确保裁剪完成后 Mapper/Actor 正确更新。
  - **交互稳定性优化**（参考 4.5）：
    - **离群点过滤与 Clipping Range 管理**：在转换时剔除无效点，并在每帧渲染前根据有效 Bounds 重置 Clipping Range，解决 Z-fighting 花屏。
    - **渲染调度优化**：在交互事件（如 `OnMouseMove`）中调用 `widget->update()` 代替 `renderWindow()->Render()`，利用 Qt 事件循环平滑帧率。
    - **QVTK 兼容性**：确保 `QSurfaceFormat` 正确设置。

- 阶段 4：验收与监控
  - 验收指标：
    - 帧率：目标场景下 ≥ 30FPS（或项目要求）。
    - 延迟：处理与显示端到端延迟满足交互需求。
    - 资源占用：CPU/GPU 占用在目标硬件可接受范围。
  - 监控与日志：
    - 记录转换耗时、渲染耗时与丢帧统计；
